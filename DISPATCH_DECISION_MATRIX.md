**Program:** Dispatch

**Status:** Working Review Tool  
**Authority:** Mike Zachary remains final authority  

## 1. Purpose

This document is used to harvest useful findings from Claude, Jules, Copilot, and any future reviewer without letting any outside proposal automatically become Dispatch doctrine.

The goal is simple:

- Keep what strengthens Dispatch.
- Modify what is useful but imperfect.
- Reject what conflicts with Dispatch authority, purpose, or operating reality.
- Defer what may be useful later but does not belong in the MVP.

No reviewer decides. No AI decides. Mike decides.

## 3. Decision Buckets

### KEEP

Items that are immediately valuable, consistent with Dispatch doctrine, and should be promoted into the next blueprint.

Initial KEEP candidates:

- Five-layer architecture: Authority, Presentation, Organizational, Deterministic, Cognitive.
- Portal as required Presentation Layer.
- Mike Zachary as final authority.
- Dispatch Spine as deterministic runtime machinery.
- Manager as event-driven and exception-driven Run Office function.
- Manager not being a direct Mike chat interface.
- Mike working through Portal actions.
- Consequence-based Portal levels: Silent, Status, Review, Decision, Conflict, Authority.
- Deterministic state registry concept.
- Deterministic routing table concept.
- Deterministic validation layer.
- Audit trail and event log concept.
- Work item lifecycle concept.
- Approval lifecycle concept.
- Library lifecycle concept.
- Archive lifecycle concept.
- Intelligence layered model: Sweepers, Acquisition, Parsing, Scoring, Intelligence Analyst.
- Publisher lifecycle concept.
- Test-Grounds to Hold to Dispatch promotion path.
- Phrase: Maximum capability, minimum authority, complete traceability.

### MODIFY

Items that are directionally useful but need correction before adoption.

Initial MODIFY candidates:

- Archive immutability: revise to preserve-by-default with purge only through approved retention policy.
- Hashing/provenance: replace MD5 with SHA-256 if cryptographic hashing is used.
- Approval language: replace physical click with authenticated Portal approval event.
- Technical stack choices: keep as proposal only until selected by Mike.
- PostgreSQL, queues, object storage, JSON Schema, Pydantic, Zod: treat as build proposal, not doctrine.
- WORM storage language: evaluate for practicality before adopting.
- Agent Governance Law references: resolve against current Constitution and clean repo authority map.
- Quality Control Review: define when mandatory versus optional.
- Portal external user views: preserve as architectural need, phase implementation carefully.

### REJECT

Items that conflict with Dispatch direction, authority model, or current architecture.

Initial REJECT candidates:

- Dispatcher Agent as a current cognitive role name.
- Any return to the 11-agent mesh as current architecture.
- Autonomous load booking.
- Autonomous contract commitment.
- Autonomous government packet submission.
- AI approving facts, truth, packets, rates, compliance, or final documents.
- AI self-modifying prompts.
- AI self-modifying code.
- Hidden decisions outside Portal visibility.
- Direct external access to internal databases.
- Manager as probabilistic LLM router for routine state transitions.
- Manager as direct conversational interface replacing Portal.
- Refinement Analyst as a standing adversarial agent.
- Controlled aggression as a permanent role.

### DEFER

Items that may be valuable later but should not block MVP build planning.

Initial DEFER candidates:

- Full driver/customer/broker multi-user Portal implementation beyond basic architecture preservation.
- Real-time ELD or telematics integration.
- Advanced RAG/vector database sync.
- Fully automated government portal API submission.
- External customer self-service dashboards beyond controlled visibility windows.
- Advanced analytics and trend reports.
- Improvement Bot or continuous improvement automation.
- Large-scale permission matrix beyond MVP access controls.
- Complex multi-agent orchestration.
- Advanced marketplace or commercial packaging for other owner/operators.

## 5. Promotion Rules

A finding may be promoted into the final Dispatch blueprint only if it passes all checks:

1. It does not violate Mike's final authority.
2. It does not create autonomous approval.
3. It does not bypass Portal visibility.
4. It reduces or protects cognitive load.
5. It fits the clean architecture model.
6. It is understandable to a future developer.
7. It can be tested or reviewed.
8. It belongs in MVP or is clearly marked deferred.

## 6. Final Blueprint Assembly Rule

The next blueprint should be assembled only from:

- KEEP items.
- MODIFY items after correction.

The next blueprint should not include:

- REJECT items.
- DEFER items except in a clearly marked future roadmap.
- Reviewer language that conflicts with Dispatch naming or doctrine.
